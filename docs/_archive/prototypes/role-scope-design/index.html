01

结论：有必要区分，且当前系统已经区分了

三级角色不是三种「名字」，而是三条权限生效范围的边界。当前系统通过 roles.kind（platform / tenant / application）已经实现，无需重构；建议只做三项轻量强化（见 07）。

论证一 · 安全

爆炸半径控制

作用域 = 最小权限的天然实现。应用角色被误配或泄漏，损失限于单个应用；租户角色限于一个租户；平台角色才是全局。混在一个池子里，「爆炸半径」永远是全平台。

论证二 · 判权

码域互斥，判权才可信

平台码（iam.tenant.manage）只授平台角色、租户码只授租户角色、应用角色只发应用域与业务码。判权时按绑定作用域过滤角色——混池后「这个角色在哪个范围生效」将无法回答，capabilities 的两层结构也随之塌掉。

论证三 · 业务

三种真实的授权单元

平台方自管（SaaS 运营）、租户 IT 管全局（企业治理）、按应用授权（外包团队只管一个应用）——第三种是 B2B 最常见的售卖/协作单元。不分应用级角色，就无法支撑「只给这个应用开权限」。

什么时候可以不区分？ 单租户 + 单应用 + 无多租户销售计划的内部小系统，一层角色足够，区分属于过度设计。本项目是多租户多应用 IAM 平台（DeerFlow 业务试点 + 多应用接入中），区分是必要项。

04

反事实推演：如果不区分会怎样

假设把三种角色放进同一个池子（不按作用域过滤）。以「应用管理员」为起点，四步即可顶格提权；每一步对照当前系统的拦截点。

    05

    一次请求的判权链：作用域在哪一步生效

    当前系统 evaluate_access 的真实链路。作用域过滤发生在第 ③ 步——这是三级角色「区分」在机制上的落点。

    ①

    请求四元组

    user · tenant · application · code
    check(user, tenant_id, application_id, "iam.application.manage")

    →

    ②

    有效角色并集

    直连绑定 ∪ 活跃用户组继承
    list_effective_roles(user, tenant, application)

    →

    ③

    作用域过滤 ★

    租户域角色（application_id 为 NULL）→ 该租户全应用生效；钉住应用的角色 → 仅匹配应用时入选；平台角色 → 仅平台租户 membership 生效

    →

    ④

    码判定

    幸存角色的授权码并集是否包含 code；业务码再查 RoleDataScope 数据范围策略（缺策略即拒绝）

      07

      可选优化：轻量强化，不做重构

      区分机制已完整，以下三项只提升「可感知性」，均为小改动，可按需采纳。

      改动小 · 1 页

      角色目录 kind 可视化

      平台侧角色目录（/admin/roles）为每行加「平台 / 租户 / 应用」描边 tag，并增加 kind 筛选器。管理员一眼分辨三级角色，不再需要点进详情看 kind。

      涉及：RoleManagement.vue 单页 + 后端目录接口已返回 kind（无需改动）

      改动小 · 文案级

      创建入口作用域提示

      三个创建入口天然分域（平台模式建平台角色 / 应用工作台建应用角色），在表单内加一行 hint：「本入口创建的角色仅在该范围内生效」，杜绝误解。

      涉及：角色创建弹窗 hint 文案，无逻辑改动

      零代码

      文档边界固化

      在 PRD 与对接手册补「三级角色作用域」一节：各域码表、绑定规则、判权链（本页 05 的内容落文档），作为后续接入方与接手人的权威口径。

      涉及：docs/ 两份文档各一节

      建议节奏：三项改善同一轮做完约半天量级；也可以只做第 1 项（最可感知）。确认后即可按 P386 实施。
