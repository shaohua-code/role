PRD · ROLE CREATION SCOPE & GRANT CONVERGENCE · P390 候选

角色创建作用域向导与授权收敛

新建角色先定作用域（平台 / 租户 / 应用），配置权限只见对应权限范围

深度：轻量迭代 状态：已实施（P390，2026-10-28）；后端加固 P1 跟进 裁决 permission-grouping PRD 的 Q1 / Q2 上游口径：PRD §3.1 三级作用域

01

背景与问题

现状两个割裂：① 新建角色时作用域是隐式的——「新建角色」弹窗只让选租户和可选的应用范围，角色是租户角色还是应用角色由「是否选了应用」倒推，创建者没有显式的作域选择步骤；② 配置权限时码集与作用域无关——授权弹窗展示全部 67 个编码（含平台专属码、租户治理码、跨命名空间业务码），给应用角色配权限时，挂了权限域不符的码也无法生效，既误导又增加误配面。

产品期望：新建角色先显式确定作用域（平台 / 租户 / 应用），应用角色必须先选租户再钉应用；作用域确定后，配置权限弹窗只展示该作用域对应的权限范围。本次同时裁决《权限编码按作用域分组 PRD》搁置的 Q1（按 kind 收敛可选集）与 Q2（租户侧隐藏平台组）。

02

已确认裁决

裁决一（平台角色新建）：不开放。创建向导仍展示三张作用域卡，但「平台角色」卡标注「由系统种子定义，不可新建」并置灰——与绿场四级角色写死、平台租户防呆（禁切类型 / 五处写入口拦截）的产品哲学一致，杜绝绕过种子再造平台超管。

裁决二（收敛口径）：严格三级矩阵。授权弹窗按角色 kind 收敛可见码集（矩阵见 FR-02），业务码仅显示角色所属应用命名空间下的编码。

04

功能需求

FR-01 新建角色作用域向导（平台控制台 · 仅 L1 可达）

第一步弹窗顶部三张作用域卡（横向等宽）：平台角色（置灰，副文案「由系统种子定义，不可新建」，不可点击）/ 租户角色（副文案「当前租户全域生效」）/ 应用角色（副文案「钉住单个应用生效」）。默认未选中，未选择时后续字段不渲染；点击卡片选中（黑边 + 浅底），再次点击已选卡可切换到另一张
第二步 · 租户角色显示「所属租户」必选（活动租户下拉）；不显示应用范围字段
第二步 · 应用角色显示「所属租户」必选 → 选中后显示「所属应用」必选（该租户活动应用下拉，联动过滤；切换租户时清空已选应用）
切换作用域切换卡片时清空已选租户 / 应用，避免跨作用域残留
保存规则提交字段与现状一致（租户 + 可选应用 + key + name + description），作用域由「是否钉应用」落到既有接口；仅文案与必填校验随向导变化：应用角色时应用为必填（现状为可选，这是行为变更点）
编辑场景编辑弹窗不出现向导（作用域创建后不可改，维持现状只读展示），但作用域行文案升级为显式域名（如「应用角色 · DeerFlow」）

FR-02 授权弹窗作用域收敛矩阵

角色 kind可见码组隐藏
平台角色（仅种子 platform.super_admin）全部七组（含平台专属、业务码全命名空间）无
租户角色租户治理 · 成员协作 · 应用域 · 模型 / 主题 / 审计平台专属 · 业务码（全命名空间）· 其他
应用角色（含自定义）应用域 · 成员协作 · 模型 / 主题 / 审计 · 业务码（仅本应用命名空间）平台专属 · 租户治理 · 业务码（其他命名空间）

规则：隐藏组整体不渲染（非置灰）——域导航、组头、计数、摘要 chips 全部不出现，恢复筛选时也不可见；「其他」组仅平台角色可见。禁选逻辑不变：自定义角色的 4 个授权权码在可见组内置灰，停用码仅可撤销。矩阵口径从三级作用域模型与 P383 模板码集推导（每组出现在哪些模板角色中即对哪些 kind 可见），与《产品需求》§3.1 同源。

FR-03 收敛的判定来源与一致性

kind 来源角色目录接口已返回 kind；两调用方（角色管理页 / 应用工作台角色 Tab）打开弹窗时传入角色 kind，弹窗不再依赖入口推断。应用工作台入口角色恒为应用角色（kind=application），行为与现状一致
业务命名空间应用角色的业务码过滤以应用 permission_namespace 为准（编码首段匹配）；应用工作台入口天然只载本应用目录，平台入口需按角色的钉定应用过滤
一致性收敛矩阵与《权限编码按作用域分组 PRD》共享组口径（utils/permissionGroups.ts 单一映射）；隐藏不改变任何判权与保存契约——后端校验保持现状，加固列 P1
