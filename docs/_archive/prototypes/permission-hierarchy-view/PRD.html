权限编码两类分组（平台编码 + 应用业务编码）

轮次：P395（修订版，替代层级三卡方案） 前置：P393 作用域分组 / P383 模板码集 / P390 收敛矩阵 状态：已批准实施（2026-10-28）

1. 背景与决策

P393 将目录页分为四个互斥作用域组（平台 6 / 租户 6 / 应用 15 / 业务码），用户先后反馈两级问题：先指出「权限编码要有层级关系——平台编码负责平台的所有，应用负责应用相关所有」；评审层级三卡方案（平台层级 27 / 租户层级 21 / 应用层级 15）后进一步收敛为两类分组：「这里是不是只要分两种——平台编码，和一种租户下的应用业务编码。」

两类分组成立的原因：管理面 27 个码全部由平台统一定义与管理（catalog_namespace=platform），授权给哪一级管理员（L1/L2/L3）是模板码集的分层持有关系，不需要拆成三组展示；业务码由租户下各应用自助登记（catalog_namespace=应用命名空间），与平台编码是两种性质。

两类分组（唯一口径） ① 平台编码：27 个管理面码——平台负责的所有管理能力；内部以「层级起点」标记表达四级角色的分层持有（L1 持 27 ⊃ L3 持 21 ⊃ L2 持 15）。② 应用业务编码：租户下各应用命名空间的业务码（动态 N 个），按应用分组展示。

3. 共享规则：两类定义与层级起点

类判定数量说明
平台编码catalog_namespace = platform（五域管理面码）27平台统一定义与管理；四级管理员按模板分层持有：L1 持 27 ⊃ L3 持 21 ⊃ L2 持 15，用「层级起点」标记表达
应用业务编码catalog_namespace = 应用命名空间N（动态）租户下各应用自助登记，按应用命名空间分组；绿场重置后当前为 0

平台编码内部的「层级起点」标记沿用 P393 归属表（resolvePermissionScope），回答「这个码从哪一级管理员开始持有」：

层级起点码数码
L1 专属6platform.overview.read、platform.tenant.read/manage、platform.account.read/manage、rbac.role.manage
L3 起6org.read/manage、rbac.role.read、rbac.permission.manage、rbac.app_role.assign、ops.model.manage
L2 起15app 3 + rbac.app_role.read/manage + org.member/group/invite 5 + rbac.permission.read + ops 4（其余管理码）

验算：6 + 6 + 15 = 27；层级起点即模板持有差集，与 P383 模板码集（L1=27 / L3=21 / L2=15）逐一对账一致。

4. 功能需求

FR-01
目录页：两类统计卡带与筛选

触发：进入权限编码目录页。结果：卡带从四张作用域卡改为三张两类卡，点击即筛选。

  • 卡带三张：00 全部（27 + N，附活动数）、01 平台编码 27、02 应用业务编码 N；编号沿用账本式样式。
  • 点击卡片即筛选；与权限域下拉（功能五域，保留为二级维度）、命名空间、搜索叠加过滤；再点当前卡或点「00 全部」清除。
  • 应用业务编码卡数量为 0 时保持概念位置灰不可点（延续 P393 行为）。
  • 列表默认排序：平台编码在前（组内按层级起点序 L1 专属 → L3 起 → L2 起，再按编码字母序），应用业务编码在后（按命名空间 + 编码字母序）。
DEMO · FR-01 两类卡带与平台编码层级标记（点击卡片切换）
平台编码行尾的层级起点标记表达四级角色分层持有；应用业务编码（绿场后暂无）按应用命名空间分组。
FR-02
目录页：平台编码行的层级起点标记

平台编码行的描述文案后附加轻量标记（L1 专属 / L3 起 / L2 起），业务码行不标记（其命名空间即归属）：

  • 标记让「平台编码负责所有，但四级管理员各拿哪些」一眼可辨，替代被取消的三层卡带承载层级信息。
  • 标记来自既有 resolvePermissionScope 归属，零新增规则；不新增表格列，附着在权限编码列描述后。
FR-03
授权弹窗：导航两类化与收敛矩阵按层级起点改写

触发：管理员打开「配置权限」弹窗。结果：左栏导航从作用域四组改为两类（平台编码 / 业务码），各角色可见码集与改造前完全一致。

  • 导航组：全部 → 平台编码（该角色可见的管理码）→ 业务码（应用角色仅本命名空间）；组头保留「已选 / 总数」计数与折叠。
  • 收敛矩阵由「隐藏作用域组」改写为「按层级起点排除」，结果等价：平台角色（L1）无排除；租户角色（L3）排除 L1 专属 6 码（原：隐平台组+业务码组）；应用角色（L2）排除 L1 专属+L3 起 共 12 码（原：隐平台组+租户组+治理码黑名单），业务码仅本命名空间。
  • 历史已持有的越层码豁免排除（可撤销，不静默剥夺）；自定义角色授权权码禁选（P383）不变；保存链路（勾选 → 预览 → PUT）报文与判权零改动。
  • 右栏码项保留 P394 行式列表（单列全宽、选中左墨色竖条）；业务码命名空间二级分组保留。

5. 交互细则与边界

场景行为
「00 全部」与「01 平台编码」区别仅在业务码（全部含业务码 N）；两入口都保留以维持清筛选习惯
业务码为 0（绿场现状）「02 应用业务编码」卡置灰显示「暂无业务应用」；平台编码卡不受影响
层级标记与筛选叠加层级标记是行级展示，不提供独立筛选维度；需要按层找码时看标记即可（L1/L3/L2 模板持有关系固定，无需筛选）
弹窗窄屏（<760px）导航降级横滑 tabs（既有行为），tab 名为「全部 / 平台编码 / 业务码」
未来新增管理码按 P383 模板归属确定层级起点，标记与两类分组自动随 resolvePermissionScope 推导

6. 验收要点

  • 目录页卡带恰为「全部 27+N / 平台编码 27 / 应用业务编码 N」；点「平台编码」27 码带 L1 专属 6 / L3 起 6 / L2 起 15 标记，与 P383 模板码集对账一致。
  • 点「应用业务编码」显示按命名空间分组的业务码（绿场后为空、卡置灰）。
  • 弹窗以 L1 / L3 / L2 三种角色分别打开：L1 见平台编码 27 + 业务码全部；L3 见平台编码 21（无 L1 专属）+ 无业务码；L2 见平台编码 15（无 L1 专属、无 L3 起）+ 业务码仅本命名空间——与改造前可见码集逐码一致。
  • 历史已持有越层码在弹窗可见可撤销；保存报文与改造前逐字节等价（同勾选集）。
  • 深浅主题与窄屏样式无破损。
