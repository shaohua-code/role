## 0. 一句话

业务项目通过 **OIDC 授权码 + PKCE** 登录，用 **SDK 2.0.0** 调 `POST /api/v1/authorization/check`；**业务权限必须带可用 `data_scope`**，否则 SDK fail-closed。

## 1. 接入步骤（对照 plan-a/07）

1. 控制台（L1）创建租户（若无）→ 创建应用 → 保存 `client_id` / `client_secret` / redirect（secret 只显示一次）。  
2. 在应用 namespace 下登记业务权限码（控制台「权限目录」或 API；见 §4 同步工具）。  
3. 系统创建应用时已自动放置 `app.admin` / `app.member`；业务角色可另建。  
4. 为 `app.member`（或业务角色）配置 **RoleDataScope**（常用 `self`）。缺策略 → `data_scope_policy_missing`。  
5. 业务侧 OIDC：校验 `iss` / `aud` / `exp`；会话租户以 token 为准，**禁止信请求头租户**。  
6. 引入 SDK 2.x：`IamAuthorizationClient` +（可选）`IAMFastAPI.require_permission` / Express `requirePermission`。  
7. 受保护 API：`require(permission)`；列表用返回的 `data_scope` 过滤（`compile_postgres_data_scope`），**先 AND 租户隔离**。  
8. 联调：L4 有 scope 通过；缺 RoleDataScope 失败；跨租户 token 403。

控制台向导已下线（归档 `_archive/integration`）；将来接入时按本文与 plan-a/07 手工配置即可。

## 2. Breaking（相对 1.x）

| 旧行为 | 2.x |
|--------|-----|
| `include_data_scope` 默认 false，可能「有权无范围」 | 业务码必须可用 `data_scope`，否则 SDK 失败 |
| alias 未登记行为不一 | `permission_map` 未登记 → LookupError / 启动失败 |
| 包版本 1.x | **major 2.0.0** |

管理码 `iam.*` 不要求 data_scope。

## 4. 权限清单同步（L1 / L2）

- **L1 平台目录：** `GET/POST /api/v1/admin/permissions`（需平台管理 JWT）。  
- **L2 应用命名空间：** `GET/POST /api/v1/admin/applications/{application_id}/permissions`  
  或同路径挂在 `/api/v1/tenant-admin/...`（需应用管理权限）。  
- SDK：`IamAdminClient(api_base_url, application_id=...)`；未传 `application_id` 时走平台目录。  
- 应用侧登记的权限固定为 `surface=business` + `requires_data_scope=true`。  
- **只增不改状态**；停用走管理台 PATCH status。
- **L2 码必须属于应用 `permission_namespace`**：例如 namespace=`crud` → `crud.document.read`。创建时可传 `permission_namespace`。示例 `iam-crud-fastapi`：`crud-demo` + `crud.document.*`。

## 5. Check 示例（2.x）

业务码不要再传 `include_data_scope: false`。省略该字段时 SDK 对业务码自动请求 scope；也可显式 `true`。

```bash
curl -sS -X POST "$IAM_API_URL/api/v1/authorization/check" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"tenant_id\":\"$TENANT_ID\",\"application_id\":\"$APPLICATION_ID\",\"permission_code\":\"crm.document.read\"}"
```

期望：`allowed=true` 且 `data_scope.mode=any_of` 含合法 constraints。  
`owner_only`：constraints 必须全为 owner，且 `user_id` 等于 subject。

## 6. RoleDataScope（self）

角色授权后必须为**每个业务权限**配置数据范围，例如：

```http
PUT /api/v1/admin/roles/{role_id}/data-scopes
{"policies":[{"permission_id":"<uuid>","scope_type":"self"}]}
```

控制台：角色管理 → 数据范围。示例 `examples/iam-crud-fastapi/provision.py` 会自动写入 self。

## 8. 前端码 / 后端角色（现行默认）

管理台与业务粗粒度入口按 [plan-frontend-codes-backend-roles.md](./plan-frontend-codes-backend-roles.md)：

| 侧 | 做法 |
|----|------|
| 登录 | `GET /auth/me` 一次返回用户信息 + `roles[]` + `capabilities`（由有效角色派生的权限码） |
| 前端 | **只用 capabilities / codes 裁菜单与按钮**；不要把前端码当安全边界 |
| 后端管理 API | **`ensure_roles` / `require_roles`**（L1 `platform.admin` / L2 `app.admin@应用` / L3 `tenant.admin@租户`） |
| 业务细粒度 | SDK `require_permission` + `data_scope` 仍可用；会话可填 `IAMUserContext.role_keys` 后用 `require_roles` |

过渡期：`ensure_management_permission(code)` 仍可用，内部已映射到角色门禁；新路由请直接写角色。

### 三级角色作用域（对接必读）

业务侧申请角色授权时按生效范围选对层级：**租户角色**（`tenant.admin`，租户全域含全部应用）、**应用角色**（`app.admin` 钉住单应用，15 管理码 + 应用命名空间业务码）、**应用成员**（`app.member`，零管理码，业务码由管理员授予）。判权按作用域过滤——钉住 A 应用的角色在 B 应用的 `check` 中不入选；租户域角色对同租户任意应用生效。业务码必须登记在应用自己的 `permission_namespace` 下并配 `RoleDataScope`（缺策略默认拒绝）。设计论证见 `docs/prototypes/role-scope-design/`。

## 11. 应用资源树下发（P357：菜单 / 按钮 / 数据规则）

> **正式方案（2026-10-29）：** 本节描述的应用资源树为现行正式能力，与权限编码并存；详见 `docs/配权说明书.md`。旧文档「不建 Resource / 资源≈权限编码」已废除。

面向应用的显式资源树：**菜单**（一级/二级…，含路由 `path`、图标 `icon`、额外参数 `extra` JSON）为枝干；**按钮**与**数据规则**挂在菜单下作为授权叶子。角色经「配置资源」勾选获得资源子集（服务端自动补齐祖先）；业务端登录后拉取当前用户可见的整棵树渲染导航与按钮显隐。

**管理面（控制台已内置，L1/L2 均可按应用管理门禁操作）：**

| 端点（`/api/v1/admin`） | 说明 |
|------|------|
| `GET/POST /applications/{id}/resources` | 平铺清单 / 新建节点（编码应用内唯一；按钮与数据规则必须挂菜单） |
| `PATCH/DELETE /applications/{id}/resources/{rid}` | 编辑（支持移动父级，环形 409）/ 删除（有子 409；级联回收授权并刷新持有者凭证） |
| `GET/PUT /applications/{id}/roles/{role_id}/resources` | 读取角色已勾选集合 / 全量替换（自动补祖先） |

**消费端下发（业务前端用用户 token 调用）：**

```http
GET /api/v1/authorization/my-resources?client_id={client_id}
```

返回该用户有效角色（直连绑定 ∪ 活跃用户组继承）资源授权并集的**嵌套树**，仅含 `active` 节点，按 `sort` 升序、`code` 兜底排序；父节点停用时子树上提，保证业务端不丢菜单。节点结构：

```json
{
  "id": "uuid", "resource_type": "menu", "code": "project.list",
  "name": "项目列表", "description": "项目管理菜单", "path": "/project/list",
  "icon": "FolderOutlined", "sort": 0, "extra": {"badge": 3},
  "children": [ /* 按钮/数据规则/子菜单 */ ]
}
```

约定：`resource_type` ∈ `menu | button | data_rule`；`icon` 存 antd 图标名（如 `FolderOutlined`），业务端按同名渲染，未命中回落默认图标；`data_rule` 的过滤条件存于 `extra` 由业务端自行解释（不替代 RoleDataScope 行级强制）；按钮/数据规则用 `code` 做前端显隐判据即可，无需再逐码调 check（树已按角色过滤）。
