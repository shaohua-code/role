## 1. 产品概述

### 1.1 背景

AI 简历、DeerFlow、知识库等项目都需要用户登录、角色管理、数据隔离和模型访问控制。如果各项目各自建设，用户账号、权限规则和审计口径会逐渐分散，增加开发和维护成本，也容易产生越权访问风险。

本产品建设统一的身份与权限管理平台，为多个业务系统提供统一认证和授权管理能力。各业务系统通过标准接口接入，同时保留自身业务数据、业务流程及品牌样式。

### 1.2 产品定位

统一身份与权限管理平台（IAM）由统一登录中心和管理后台组成。平台统一管理身份、应用、组织、角色、权限策略、登录主题和审计记录；业务系统在自己的服务端执行平台授权结果，并负责本系统的业务数据访问控制。

### 1.3 产品目标

- 用户通过一个账号登录多个已授权业务系统。
- 管理员在统一后台管理租户、应用、用户、组织、角色和权限。
- 每个接入应用可配置独立登录页主题，包括背景图、Logo、颜色、布局和文案。
- 业务系统可基于统一身份和授权规则控制功能、数据和模型访问。
- 登录、授权变更及管理操作可查询、可审计。

### 1.4 设计原则

1. **认证集中，业务授权落地：** 平台提供可信身份和授权策略，业务服务端负责执行。
2. **默认拒绝：** 未明确授权的应用、接口、数据和模型调用均拒绝。
3. **租户隔离：** 租户是数据隔离边界，不能依赖前端传入的租户标识保障安全。
4. **最小权限：** 角色仅获得完成工作所需权限。
5. **可扩展接入：** 采用标准认证协议和稳定的权限编码，避免绑定单一业务项目。

### 1.5 成熟产品调研与设计取舍

本 PRD 参考成熟 IAM、策略授权和管理端设计的公开资料，吸收其领域模型与管理能力，不复制产品界面或实现细节。

| 参考方案 | 成熟做法 | 本项目采用方式 |
|---|---|---|
| Keycloak | Realm 隔离身份与客户端；Group 可承载成员和角色映射；Authorization Services 将 Resource、Scope、Policy、Permission 分开，并支持服务端执行及授权模拟。[管理指南](https://www.keycloak.org/docs/latest/server_admin/) · [授权服务](https://www.keycloak.org/docs/latest/authorization_services/index.html) | 租户隔离、多应用客户端、组织/用户组、资源、操作 Scope、授权策略和权限授予；高阶版本提供策略模拟和判定说明。 |

## 3. 用户角色与权限边界

| 角色 | 说明 | 权限边界 |
|---|---|---|
| 平台管理员 | 负责平台整体配置 | 可管理租户、应用和平台级安全配置 |
| 租户管理员 | 负责本租户日常管理 | 仅能管理本租户用户、组织、角色及应用授权 |
| 应用管理员 | 负责指定业务应用 | 仅能管理被授权应用的角色、成员和应用配置 |
| 普通用户 | 使用业务系统 | 只能访问已授权应用及资源 |
| 审计人员 | 检查操作和安全事件 | 可读审计记录，不可更改授权配置。**待裁决（G01① / 2026-10-29）：** 绿场四级写死 L1–L4 后无处授予该只读角色；审计接口实挂 L2 `app.admin`。改 PRD 删此行，或补独立只读授予路径，需产品拍板后再实现 |

平台管理员权限应可审计。租户管理员和应用管理员的管理操作均受租户及应用范围约束。

### 3.1 两类角色与五级平台模板（P405）

产品上角色只分两类，不要按库表 `roles.kind`（platform / tenant / application）理解成三类产品角色。`kind` 仍是实现细节，判权绑定范围不变。

| 产品类 | 有哪些 | 挂什么 | 出现在哪 |
|---|---|---|---|
| **平台角色** | 五个系统模板：`platform.admin` / `tenant.admin` / `apps.admin` / `app.admin` / `app.member`；以及未钉应用的自定义租户侧平台角色 | **只挂平台管理面码**。超管可配全部 27 码；租户 / 多应用 / 应用管理员只配自己看得见的码 | 高级管理 → 平台角色 |
| **应用角色** | 钉住应用且 key 不在五模板里的自定义角色（如财务 / 只读） | **本应用业务码 / 菜单 / 按钮**，以及操作者看得见的租户 / 应用管理码 | 应用工作台 → 角色（「应用权限」+「配置成员」） |

五级平台模板：

| 模板 key | 名称 | 平台权限范围（摘要） |
|---|---|---|
| `platform.admin` | 平台超级管理员 | 全平台 27 码；任命租户管理员 |
| `tenant.admin` | 租户管理员 | 本租户 20 码；可建删本租户应用；可任命 `apps.admin` 与 `app.admin` |
| `apps.admin` | 多应用管理员 | 与 `app.admin` 同结构钉住单个应用（管 N 个应用 = 绑 N 次），另有 `rbac.app_role.assign`，可再任命该应用的 `app.admin`；不能建删应用 |
| `app.admin` | 应用管理员 | 本应用 15 码；可维护成员与应用角色；**不能**再任命应用管理员 |
| `app.member` | 应用成员 | 平台侧只表示属于该应用，**不挂业务码**；菜单/按钮由另行绑定的应用角色决定 |

边界规则：

- 两套目录不许混：`GET /admin/permissions` 只出 `surface=management`；业务码只走应用工作台。
- 平台角色拒挂业务码；应用角色可挂操作者看得见的租户 / 应用管理码，仍拒看不见的码与外应用业务码。
- **看得见才能配：** 前四级管理员可新建角色、自由搭配自己已有 ∩ 范围内的码；看不见的码不出现、也不能勾选。系统预置角色同样：四个管理员可改本级及以下模板，不能改上级、不能挂上级码。P383「自定义角色不能含授权权码」已废止。
- 给平台成员分配应用角色时，若还没有该应用的 `app.member`，同一事务自动补绑。
- 创建/删除应用仍仅 L1 / L3（P404 保留）。`app.member` 不能配权、不能新建角色。

前端 capabilities 两层结构不变：租户域码在 `tenants[].codes`，应用码在 `tenants[].applications[].codes`。

## 5. 核心业务流程

### 5.1 新应用接入流程

1. 平台管理员创建应用并填写应用标识、名称和描述。
2. 配置登录回调地址、登出地址和来源域名白名单。
3. 配置应用 Logo 和登录主题。
4. 创建应用权限项和初始角色。
5. 业务系统接入 OIDC 登录流程及权限校验接口。
6. 管理员分配用户或角色。
7. 用户登录并访问业务系统。

### 5.2 登录流程

1. 用户从业务系统发起登录。
2. 浏览器跳转到统一登录中心，并携带应用标识及 OIDC 请求参数。
3. 登录中心根据应用标识加载该应用已发布的登录主题。
4. 用户提交账号凭据，平台执行身份、账号状态及安全策略校验。
5. 平台检查用户是否具有该应用访问权限。
6. 验证通过后返回授权码至已登记回调地址。
7. 业务系统服务端使用授权码换取令牌，并校验签名、签发方、受众和有效期。
8. 业务系统建立自己的会话，并在服务端执行后续权限检查。

### 5.3 角色授权流程

1. 管理员选择租户和应用。
2. 创建角色或选择已有角色。
3. 为角色分配菜单、功能、API 及适用的数据范围权限。
4. 将角色分配给用户。
5. 权限变化写入审计日志，并触发授权缓存失效或版本更新。
6. 业务系统按新授权结果拒绝未授权操作。

### 5.4 登录主题发布流程

1. 管理员选择目标应用并进入主题编辑页。
2. 修改 Logo、背景、颜色、布局、文案及入口开关。
3. 预览桌面端和移动端效果。
4. 保存草稿并发布。
5. 用户访问应用登录入口时看到最新已发布主题。
6. 管理员可查看历史版本并恢复上一版本。

账号规则：

- 用户标识在平台内唯一；邮箱按验证状态管理；手机号字段保留但暂不建设短信/验证通道（2026-10-27 裁决，列为后续能力）。
- 全局身份仅使用 `active | disabled | locked`：停用是管理员设置的持久禁用，锁定是管理员采取的安全控制，登录、管理 API 和 OIDC 均只允许 `active`。不得把“离职”作为全局用户状态，因为全局身份可能仍在其它租户/产品中使用。
- 全局账号停用/锁定由平台管理员执行，禁止管理员锁定或停用自己的当前账号；状态变化使用 `expected_status` + 行锁避免旧页面覆盖。服务端递增 `auth_version`、撤销所有 IAM/OIDC refresh session、消费未兑换的 authorization code/consent ticket，并在同一事务写审计。恢复启用不恢复旧会话或授权票据。
- 租户成员使用 `active | disabled | departed`：`disabled` 是可恢复的临时暂停，保留该租户角色/用户组/组织关系但撤销此租户应用 refresh session、authorization code 和 consent ticket；管理员恢复时原角色重新生效，用户必须重新登录。`departed` 是离开该租户的终态，清除角色绑定、用户组成员关系和组织归属，保留 membership 历史行及审计；重新加入必须重新邀请且只获得新邀请指派的角色。
- 租户成员状态变更不得注销该用户的其它租户/产品会话。更新发生后，IAM 在线 UserInfo/Introspection/authorization 会按成员状态即时拒绝；只离线校验 JWT 的资源方无法即时获知状态变化，访问令牌最迟在自身过期前仍可能被接受（当前 OIDC access token 默认 10 分钟）。高风险操作须使用 IAM 在线授权或 introspection，离线 JWT 的资源方必须评估并接受此暴露窗口。
- 密码不得以明文或可逆形式保存。
- 注册策略由全局紧急开关和应用级策略共同控制；默认关闭。IAM 管理台与企业租户不因 ToC 自助注册而开放注册。
- ToC 注册必须先验证邮箱；未验证身份不能登录、换取 OIDC code/token、创建租户成员或获得应用授权。
- 平台管理员可查看用户当前可续期的 IAM 管理台会话和 OIDC 业务应用会话，并按单个会话执行远程退出；撤销动作与审计同事务提交。新签发 IAM access token 绑定稳定 refresh session ID；带 `offline_access` 的 OIDC access token 绑定 refresh-token family，撤销后 IAM 在线鉴权、UserInfo 与 Introspection 立即拒绝对应令牌。旧版本无 `sid` 的短期 access token 只能自然过期；仅离线验签的业务方也可能在 token expiry 前继续接受令牌。
- 会话列表只展示会话类型、应用、client ID、创建时间和刷新凭证到期时间；当前未采集设备名、浏览器 UA、来源 IP 或最后活动时间。未请求 `offline_access` 的 OIDC 短期令牌没有可管理的持久会话记录，因此不能从该列表单独远程撤销。
- 用户身份在 IAM 全局唯一；重复注册和重发验证码响应不得泄露邮箱是否已存在。已有身份登录后才能接受额外租户/应用成员关系，禁止按邮箱自动合并。
- 注册只授予服务端为目标 OAuth 应用预先配置的活动普通角色，拒绝平台管理员角色、`iam.*`、管理 scope、跨应用/跨租户角色及 tenant/organization 数据范围；有本人数据访问权限时配置 `self` 范围。缺少有效默认角色或邮箱服务不可用时，该应用注册应保持关闭。
- 推荐首期为每个 ToC 产品建立一个专用消费租户，与企业/组织租户隔离；注册用户加入对应消费租户并只拿该应用的普通角色。个人/团队业务数据仍须由业务系统用 owner/tenant 条件隔离。不能为每个邮箱随意创建企业租户，也不能把租户成员角色当成平台管理员。

### 6.1.1 ToC 自助注册闭环

#### 用户流程

1. 用户从目标 ToC 应用的品牌登录页进入注册；只有 IAM 服务端返回该 application 的注册策略为 `open` 时才显示入口。登录主题 `show_register` 只控制视觉草稿，不能开通注册。
2. 第一屏提交邮箱、显示名称并明确勾选当前版本的用户协议/隐私政策。第一屏不渲染密码框，也不把密码保存在前端状态；营销订阅必须单独、可选，禁止预勾选。应用身份由服务端校验 `client_id` 后解析，浏览器不得提交 `tenant_id`、`role_id`、管理员标志或可信 owner 属性。
3. 创建短期待验证申请和事务发件箱。验证码只保存带独立注册密钥的 HMAC 摘要，发件箱仅引用挑战 ID 并由服务端派生同一个短码。注册密钥与 JWT signing key 分开，稳定保存在 Secret Manager；轮换注册密钥前须排空待投递 outbox，既有 challenge 需重新申请。默认验证码有效 10 分钟、错误最多 5 次、按 HMAC 邮箱及可信来源 IP 每 60 秒最多申请一次；邮箱确认前不创建活动用户、成员关系、会话或 OIDC token，也不接收/保存密码。邮件失败重试最多 5 次，不会提前激活账号。migration `0024` 清理旧 challenge 中可能暂存的密码摘要并移除该列。
4. OTP 申请成功后显示第二屏，用户提交验证码和密码；重发验证码不清空已输入密码，返回登录则清理验证码与密码。服务端在一个事务内锁定并消费申请、验证邮箱；新用户此时设置至少 12 位密码并创建全局身份，已有账号必须处于活动状态且当前密码正确。随后加入 `consumer` tenant、绑定服务端配置的同应用普通角色，写审计和用户接受的协议版本记录。角色、租户或协议策略在申请后发生变化时拒绝兑换；并发/重放只能有一个成功。
5. 成功后设置 HttpOnly refresh Cookie 并回放原 OIDC authorize URL。已有 IAM 身份可以使用注册入口加入新 ToC 应用，但必须同时证明邮箱和原密码；系统不自动合并身份、不覆盖原密码。既有账号的密码可能少于 12 位，不套用新账号的密码长度要求。

#### 身份模型与注册决策

- 一个邮箱对应一个 IAM 全局身份；未来不同业务项目可配置各自的 OAuth Application、品牌登录主题和消费 tenant，同时复用身份/密码。用户在不同产品的成员资格和角色分别授权，注册一个产品不自动加入其他产品。试点应用已随 P392 下线待重新对接，AI 简历和知识库的旧 IAM 接入已清理。
- 当前 Application 固定属于一个 tenant；首期每个彼此独立的 ToC 产品环境绑定专用 `consumer` tenant。普通租户默认为 `organization`，不能开放公开注册；租户下所有应用都先关闭注册才允许切换类型。若产品要支持用户自主选择企业/工作区或一个 Application 下多个客户 tenant，必须先做经过验证的 tenant discovery/选择和 OIDC 上下文改造，不能接受浏览器直接传 tenant ID。
- 首期注册方式为邮箱验证码 + 密码；验证码确认前只存在有 TTL 的待验证 challenge。手机号、社交账号、邀请码/审批注册、Passkey/MFA 作为后续能力，不能与“创建 IAM 管理员/企业租户”混为一类。
- 该自助注册与 DeerFlow 的 OIDC 首登开户是两段不同的生命周期：IAM 注册负责创建并验证全局身份及目标应用 membership；DeerFlow 首登仅在 OIDC `iss/aud/nonce/signature/sub` 校验成功、且 IAM 已允许该应用登录后自动创建本地 `system_role=user`。DeerFlow 本地用户主键绑定稳定的 `(issuer, sub)`，不能只用可变邮箱关联。邮箱、`email_verified`、旧 `admin_emails`、前端标志或租户默认配置均不授予管理员；管理能力来自 IAM 显式授权并由 DeerFlow 服务端在线复核。加密 vault 和 Gateway/Agent 相关权限映射已有源码，正式配置、角色授权与真实联调尚未验收。
- 禁用/离职 membership 不能借公开注册端点复活；已离职成员必须重新邀请并只获得新邀请指定的角色。另一个产品中的活动身份不因本应用注册、退出或离职而被全局禁用；全局锁定/停用由 IAM 撤销跨应用会话。
- 重复注册本产品时以同一全局身份加入既有成员关系，不创建重复用户；另一产品复用同一邮箱时必须证明邮箱且输入当前 IAM 密码。未来若支持密码重置或邮箱变更，应按全局 IAM 身份处理，并撤销旧会话；不能由某一个产品无提示更改共享凭据。
- 用户生命周期包括全局账号锁定/停用、租户成员暂停/离职、密码重置、凭证撤销和产品退出。首期用户自主导出/删除账号、删除后的财务/审计留存以及账号数据恢复规则尚未实现，产品上线前由业务/法务确认并加入账户中心路线图。
- 新注册账号完成邮箱验证后可进入对应产品，但不代表业务 API 自动放行。默认角色的业务权限、`self` 数据范围、应用/tenant claim、本地用户映射及每条 API/检索/异步任务的 owner 过滤都须分别联调。
- 公开注册与模型成本要一起设计：新用户不能获得 Provider 密钥或绕过服务端网关；模型权限与用量额度必须按用户/租户在 Provider 调用前鉴权和预留。当前 `MODEL_QUOTA_ENFORCEMENT_ENABLED=false`，产品没有确认试用额度/付费策略且资源方没有验证网关强制前，不得把可产生费用的 AI 能力面向新注册用户开放。模型额度不足或中心配额服务不可用时应拒绝调用并给出可恢复提示。

#### 应用注册策略与授权

- 全局 `ALLOW_PUBLIC_REGISTRATION` 是紧急总闸，默认 `false`；每个 OAuth 应用支持 `disabled | open`，默认 `disabled`。只允许平台/租户/应用管理授权范围内的管理员更新其应用策略；首期不提供 `approval` 审批态。
- 全局开放时必须在 Secret Manager 注入至少 32 字符的独立 `PUBLIC_REGISTRATION_SECRET`；禁止复用 `JWT_SECRET`。JWT signing key 轮换不得使 OTP/outbox 失配；注册专用密钥轮换则会让未消费 challenge 失效，运行手册须先暂停/排空队列。
- 开放策略必须同时绑定：活动 OAuth Application、活动且类型为 `consumer` 的 ToC 租户、同租户/同应用/活动的普通默认角色、用户条款/隐私版本、已发布主题中的两个政策链接、已展示注册入口以及可用 SMTP。所有存量租户由 migration 默认归类为 `organization`；管理台只有在该租户全部应用注册关闭后才允许切换类型。任何关联缺失或跨租户/跨应用时服务端拒绝启用/验证。challenge 保存当时的政策 URL 和版本；申请发码及兑换都与当前值比较，任一变化都会拒绝旧 challenge。主题链接应指向不可变版本文档，更新正文必须递增对应版本。
- `approval` 创建待审批注册申请，不能签发会话或 OIDC token；批准人只能为该应用分配允许的普通角色，并记录审批人、时间和原因。首期可先实现 `open` 与 `disabled`，审批列入后续能力。
- 注册普通角色只能授予产品基本使用权限，不能包含 `iam.*`、平台管理员、应用密钥、角色管理、模型凭证管理等管理能力；不能绑定 tenant/organization/organization_tree/selected_organizations 数据范围；用户本人数据权限使用 `self`。IAM 层只作硬性拒绝，产品仍须检查每条数据查询的 owner 约束。
- 当前 OAuth Application 的 `tenant_id` 固定且 OIDC membership 检查要求用户加入该租户。首期推荐为每个 ToC 产品预置一个专用消费租户，避免为每个个人用户新建 IAM tenant，也避免使用企业客户租户；如果要支持每人独立 IAM tenant，须先重构 Application/client 的多租户授权上下文与 OIDC tenant 选择，不能只修改注册路由。

#### 风控、隐私和运维要求

- 注册申请接口对已注册邮箱、已停用账号和节流请求返回同样文案；验证码兑换失败统一返回无效/过期，不返回邮箱存在状态。现有节流使用 HMAC(email/app) 和 trusted client IP 冷却；IP 只能来自受信代理配置，不能信任浏览器自报头。`/oidc/login-context` 返回公开冷却秒数，注册页倒计时使用服务端值而非固定常量。默认每邮箱/IP 60 秒冷却不是全局/每日邮件配额，公网上线还要由邮件供应商和 WAF 设置产品级日/小时额度、异常 IP/域名监控和熔断；高风险开放注册前评估 CAPTCHA/自适应风控。
- 初期只开放邮箱验证；SMTP 发件域上线前须配置 SPF、DKIM、DMARC。事务发件箱使用行锁租约、指数退避和最多 5 次投递重试；全局开关关闭、应用/租户/角色停用后停止发旧验证码。日志不记录密码、验证码、token、邮箱或完整邮件正文。退信/队列积压看板、SMTP 日/小时配额和 CAPTCHA 尚未实现，上线前需配置邮件供应商上限、反向代理/WAF 风控并完成运维监控。
- 使用 Argon2 哈希密码；验证码/令牌一次性消费，短 TTL，过期记录定期清理。邮箱 OTP 之前的 challenge 不接受、不存储密码，只短时保存邮箱、名称、政策版本/URL；同意记录保留用户、应用、政策版本/URL、时间和必要的可信来源 IP，不覆盖旧版本。当前只有注册成功审计事件，注册转化/邮件送达/滥用指标看板待建设；分析事件中邮箱须脱敏或用不可逆伪名。
- 账号状态、未验证邮箱不能用来绕开禁用、密码重置、刷新会话撤销和 OIDC 即时成员/角色校验。账户删除/导出、隐私保留期限和地区合规需上线前由业务/法务确定。
- ToC 用户的数据可见性不由“加入消费租户”推导。产品 API、模型调用、文件/检索、后台任务必须继续以服务端身份执行本人 owner 过滤；IAM tenant membership 与业务资源归属是两种边界。

### 6.1.2 注册上线的产品与运营门槛

- **目标用户和租户边界：** 公开注册只对明确的 ToC 登录域开放。每个独立产品/环境指定消费 tenant、OAuth Application 和该应用普通默认角色；一个产品的注册不能自动加入其他产品。IAM 管理台、企业租户、员工后台及合作伙伴管理账号继续邀请/管理员创建。
- **身份与账号恢复：** 邮箱是 IAM 全局登录标识。重复注册统一返回提示，不按邮箱自动合并；新应用加入既有身份需邮箱 OTP + 当前密码。密码找回只改全局密码并撤销全局刷新会话。邮箱变更、账号锁定/停用和成员离职分别说明影响范围；离职成员不能从公开端点复活。
- **权限与数据：** 注册只绑定服务端选出的同应用普通角色；客户端不能提交 tenant、role、scope、管理员属性或业务 owner。新账号不因通过身份验证就取得跨组织数据；产品 API、文件/向量检索、异步任务和模型调用都按可信服务端用户 ID 与业务数据 owner/tenant 过滤。
- **反滥用：** 当前代码有按 HMAC 邮箱/应用及可信 IP 的 60 秒冷却、OTP 失败上限、短期 challenge、统一申请文案和邮件 outbox 重试；它没有全局/每日邮件额度、退信指标看板或 CAPTCHA。公开开放前必须配置 SMTP 供应商每日/每小时硬额度、WAF/IP 异常告警、失败与退信监控、队列积压告警和一键关闭流程；面向公网规模后增加 CAPTCHA/自适应风控、一次性邮箱与代理滥用策略。
- **隐私与合规：** 注册只收完成账户所需的邮箱和显示名称；用户协议/隐私政策需版本化并可访问。营销同意须可选且不得默认勾选。地区、年龄门槛、敏感数据、第三方模型处理、数据导出/删除、审计证据保留期限和账号注销后的业务数据处理由产品/法务上线前评审。
- **用量与收费：** 公开注册前明确试用额度、按用户/tenant 的费用上限、滥用扣额和超额提示。模型额度执行当前默认关闭；Gateway 未能在 Provider 调用前完成授权、预留和结算时，不对新注册账号开放可产生费用的模型能力。
- **灰度和指标：** 先内部测试、再小规模 ToC 灰度、最后逐产品开放。监测验证码投递/退信/重试、OTP 成功率、注册完成率、IP/邮箱节流、账号停用和模型费用；分析事件使用脱敏邮箱或不可逆标识。发现邮件轰炸、异常注册或成本突增时先关闭总闸并可单应用停用。
- **发布验收：** 从品牌登录主题进入注册，在桌面和手机完成新邮箱 OTP、短密码拒绝后修正、已有 IAM 账号加入应用、错误/过期/重放验证码、政策更新、SMTP 故障、限流、停用账号和离职 membership 拒绝；确认只创建一条身份/成员/角色/同意记录，响应不泄露邮箱是否存在；演练关闭总闸及重新开放。

#### 验收范围

- 注册开关关闭、邮箱未验证、邮件故障、角色缺失/停用/越权、租户/应用不匹配时，不能创建活动会话、membership、授权码或 token。
- 验收覆盖验证码成功、错误上限、过期、重放、重发冷却、并发重复请求、大小写邮箱、已注册邮箱统一响应、已有 IAM 身份当前密码校验、邀请冲突、SMTP 重试、审计脱敏和多租户 owner 数据隔离。
- DeerFlow 验收覆盖首次 OIDC 登录只创建普通用户、稳定 subject 绑定、防止同邮箱异身份自动合并、email/admin 配置不提权、IAM 明确授权/撤权后 Gateway 管理能力按服务端在线状态变化；管理员权限撤回和 tenant/member 停用必须有负向测试。普通注册账号不得获得模型供应商凭证，模型调用须验证权限、用户/租户额度及失败关闭行为。
- 管理台可配置受权限约束的注册策略、同应用默认角色和条款版本；主题页配置政策 URL 和入口展示，公开登录页只显示服务端允许的入口。浏览器控制台检查与端到端邮箱/数据库链路尚未验收。

#### 参考成熟身份平台的官方文档

- Auth0 建议在使用邮箱联系用户、按邮箱索引或允许创建关联账号前验证邮箱，并说明链接验证可能被邮件扫描器/用户误触；OTP 可要求用户主动输入验证码：[Verify Emails using Auth0](https://auth0.com/docs/manage-users/user-accounts/verify-emails)。
- Amazon Cognito 将新账号保持为 unconfirmed，直到用户提交确认码后才允许登录，并明确验证联系地址的目的：[Signing up and confirming user accounts](https://docs.aws.amazon.com/cognito/latest/developerguide/signing-up-users-in-your-app.html)。
- Auth0 将 bot detection、IP throttling、brute-force protection 和 breached-password protection 作为分层保护措施：[Attack Protection](https://auth0.com/docs/secure/attack-protection)。
- OpenID Connect Core 明确只有 `iss + sub` 能作为 relying party 可依赖的稳定用户标识；email 可能变化，也允许同一 issuer 在不同时间把相同 email 值用于不同 End-User。因此多产品身份关联和 DeerFlow 首登绑定使用 `(issuer, sub)`，不能只凭邮箱合并或授予角色：[OpenID Connect Core 1.0 §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)。

### 6.3 应用管理

管理台应用目录由独立 `frontend/src/features/applications/ApplicationManagement.vue` 维护。创建表单和 `schemas/applications.py` 的 `ApplicationCreate` 均强制至少一个登录回调、最多 20 个；路由再校验每个 URI 为 HTTPS 或 localhost/127.0.0.1 的 HTTP，不含 URL 凭据/片段。绕过前端不能创建缺少登录回调的 OAuth 客户端。创建后，租户、Client ID 和回调白名单在当前 PATCH API 中只读，资料编辑仅改名称/说明。启停提交 `expected_status` 与目标状态，服务端行锁检查旧状态，冲突返回 409；停用与会话撤销、审计在同一事务提交。受信切换和立即轮换密钥仍有影响确认；密钥明文仅展示一次，关闭弹窗时清除。

应用配置项：

- 应用名称、唯一标识、图标、描述和状态。
- OIDC 客户端 ID 与客户端密钥管理。
- 登录回调地址和登出回调地址白名单。
- 应用管理员及授权用户范围。
- 登录主题和权限项（与 `permission_namespace` 绑定的稳定权限编码目录；业务权限在应用内维护，全局 code 仍唯一）。

安全规则：

- 回调地址必须与登记白名单精确匹配，不允许开放通配回调。
- 客户端密钥仅用于服务端，不得发给浏览器。
- 支持密钥轮换；查看密钥时只显示一次，之后仅显示掩码。
- 停用应用后，新的登录授权请求必须失败。

### 6.5 角色、资源和操作权限

权限采用“主体—资源—操作”的表达方式：用户或角色作为主体，在租户/应用范围内，对资源类型或具体资源执行一个或多个操作 Scope。菜单和按钮由权限编码映射展示，不作为独立的安全边界。

权限类型：

- **应用访问：** 是否允许用户进入某个应用。
- **菜单权限：** 是否显示指定导航和页面入口。
- **资源权限：** 可管理某类资源或具体资源，例如应用、用户、知识库。
- **操作 Scope：** 可对资源执行查看、创建、编辑、删除、导出、运行等动作。
- **API 权限：** 服务端路由到资源类型和操作 Scope 的映射。
- **数据范围：** 用户可查询或修改的业务数据范围。
- **模型权限：** 可使用的模型及能力，后续阶段建设。

功能要求：

- 平台角色、租户角色、应用角色范围明确，默认不得跨租户继承。
- 同一全局用户可加入多个租户，并在每个租户拥有不同角色。
- 支持创建、编辑、复制、停用角色。
- 支持按资源类型及操作 Scope 分配权限，并映射到菜单与按钮。
- 支持查看用户有效权限及来源（用户直授、组/组织、角色）。
- 平台保留授权决策日志；策略模拟与判定说明列入 P1。
- 角色停用或授权变化后，更新授权版本并使缓存失效。

权限编码示例：

```text
resume.dashboard.read
resume.resume.create
resume.resume.export
knowledge.document.read
demoapp.workflow.run
model.text-generation.invoke
```

### 6.6 数据权限

标准数据范围：

- 仅本人
- 本部门
- 本部门及下级部门
- 指定部门
- 当前租户全部数据

当前数据策略按角色与原子权限配置，V1 支持 `tenant`、`self`、`organization`、`organization_tree` 和 `selected_organizations`。同一用户多个匹配角色的策略取并集；租户级范围覆盖其他子句。本人条件必须同时匹配全局 `owner_user_id` 与 `tenant_id`，组织条件匹配 `organization_id` 并且必须 AND `tenant_id`，防止同一身份在多个租户拥有业务记录时串读。选择本人范围时业务服务须提供 `owner_user_id` 归属字段，组织范围须提供 `organization_id` 字段；接入服务必须把每个 `any_of` 子句的 `tenant_id` 编译为同一行级 AND 条件。调用授权 API 时设置 `include_data_scope=true`，响应携带 `any_of` 条件；若权限未配置数据策略、策略解析后无有效组织或组织跨租户，则默认拒绝。该响应只是可信过滤条件，业务服务仍要把它编译成自己的 SQL/检索过滤，IAM 不直接读取业务记录。

数据授权规则：

- 业务服务端必须校验用户、租户、资源归属及数据范围。
- 前端隐藏菜单或按钮不能替代后端授权检查。
- 对知识库检索，必须在召回查询过程中应用权限过滤，不能只在结果页隐藏无权内容。
- 数据权限策略应通过版本或缓存失效机制及时生效。

### 6.7 管理台外观与应用登录品牌

管理台外观配置（当前开发版提供浅/深色/跟随系统、品牌主色、舒适/紧凑密度和可折叠侧栏；个人/租户/平台偏好优先级仍为后续目标）：

- 支持浅色、深色和跟随系统三种模式。
- 支持平台品牌主色、组件圆角、界面密度（舒适/紧凑）。
- 支持标准侧栏布局和可折叠侧栏；管理员可设置个人偏好，平台管理员可设租户默认值。
- 主题使用 Ant Design Vue ConfigProvider 设计令牌与 CSS 变量驱动，不接受任意 CSS/HTML/JavaScript。
- 主题偏好分为个人偏好、租户默认、平台默认；优先级为个人 > 租户 > 平台。

应用登录品牌配置（当前开发版提供表单配置及桌面/手机预览，拖拽排版与素材上传待开发）：

每个应用可独立设置：

- Logo、应用名称、页面标题和欢迎语。
- 背景图、背景色、主题色和按钮颜色。
- 登录卡片位置、布局、宽度和圆角。
- 注册、忘记密码、验证码及其他登录方式入口。
- 用户协议、隐私政策和帮助链接。
- 登录页布局模板、登录方式开关及移动端适配。

当前主题会应用 Logo、背景、色彩、卡片和预设布局；`show_forgot_password` 控制登录页找回密码入口，SMTP 和重置接口未配置/未迁移时请求会提示服务暂不可用。`show_register` 仅是显示偏好，实际入口必须与服务端 application registration policy 取交集，主题发布不能开通注册。管理台登录入口供平台、租户和应用管理员共用；IAM 管理台仍保持引导创建首个平台管理员/邀请制，ToC 产品登录页才可按应用策略显示注册。

交互要求：

- 提供桌面端和移动端预览。
- 登录页与管理台主题彼此独立；修改管理台主题不得影响业务应用登录页。
- 支持草稿、发布、查看版本和恢复历史版本。
- 图片限制格式和大小，资源存储于对象存储，数据库只保存资源元数据和地址。
- 主题设置采用受控配置字段，不允许注入任意脚本。
- 发布前检查必填字段和主要文本可读性。

### 6.8 模型目录、用量治理与调用网关

- 管理台由独立 `frontend/src/features/models/ModelGovernancePage.vue` 提供模型目录和用量视图；支持租户筛选、目录新增/资料编辑/启停与调用汇总/最近 100 条记录，不提供供应商凭证回读或运行时配额开关。

- 维护模型名称、提供方、版本、能力类型和启停状态。
- 平台管理员可部分编辑提供方、模型名称、展示名称、HTTPS 服务端点、能力、价格、RPM/TPM 元数据和外部密钥引用；租户归属与模型标识不允许通过该编辑接口修改。凭证默认不回显，编辑时留空表示保留，显式清除需单独勾选；RPM/TPM 是否产生调用拦截仍由服务端运行时开关控制。
- 配置允许调用的应用、租户、角色或用户范围。
- 配置调用次数、Token、并发和预算限额（目录 RPM/TPM 当前只是元数据，必须由网关实现预留/扣减和并发保护后才算强制）。
- 查询调用量、成功率、失败原因和费用估算。现有开发代码新增 append-only `model_usage_events`：受信网关在调用结束后按 `X-IAM-Model-Gateway-Key` 上报身份关联、Token、结果和延迟；request ID 幂等，管理员 API 提供汇总及最近记录，管理台提供用量页。
- 用量上报服务密钥由 `MODEL_USAGE_API_KEY` 注入，至少 32 字符。仅可信服务端可使用；数据库不接收 Prompt、模型响应正文或供应商 API 密钥。
- 费用仅根据请求对应模型目录的输入/输出每百万 Token 价格估算；未维护价格时记为未知，供应商账单以其账单为准。
- **P296–P298 UI 状态（2026-10-16）：** 费用仍未展示币种，失败原因仍无账目字段。历史账目和汇总已可按模型、结果、UTC 日期筛选；待核对队列仍只按租户分页。读取故障不再伪装成空账本。P298 类型检查通过；后端测试、生产构建和浏览器故障注入尚未验证。详情见[验收记录](验收记录.md)。
- 供应商密钥只保存在外部 Secret Manager，模型目录只存秘密引用且前端只展示是否已配置；不得把密钥明文或可还原密文存入 IAM 普通业务表。
- 模型授权由 IAM 管理；实际请求代理、密钥使用和限流由模型网关或业务后端执行。

IAM 提供模型调用授权、用量账本及可选的 RPM/TPM 拦截，但不是模型代理，也不会读取供应商凭证。网关调用 Provider 前先持久化用量预留；`MODEL_QUOTA_ENFORCEMENT_ENABLED` 仅控制是否依据租户内 `model_id` 的 60 秒 RPM/TPM 限额拒绝请求，关闭或没有阈值时仍保留预留并要求结算。10 分钟仅是待核对期限：预留到期后不会按上限自动收费或释放，未处理项继续占用保守 TPM 额度并进入管理员核对队列。管理员可按 Provider 侧证据记实测/估算用量，或在明确确认未调用 Provider 后释放，操作原因与决定写审计。管理员队列分页并返回真实待核对总数，确保长期未处理的预留都可被发现和处置。网关已提交 outbox 事件可重试，但 Provider 完成与 DeerFlow 本地 outbox 提交间的崩溃无法自动还原 Token。P298 只读确认开发库 revision 0031 且 ready 200；备份文件未复核。DeerFlow 目标库、真实 Provider 和人工核对流程仍未联调，配额拦截默认关闭；请求 ID 账本和过期预留暂无归档策略。策略细节见[技术架构与接入](技术架构与接入.md)第 6 节。

### 6.9 审计日志

审计事件至少包括：

- 登录成功、登录失败、登出、密码重置、账号锁定。
- 用户新增、资料变更、启停和角色调整。
- 应用、回调白名单及登录主题变更。
- 角色、权限和数据范围变更。
- 模型授权及配额变更；IAM API 已支持 RPM/TPM reserve/settle 与管理员待核对，DeerFlow 的 LangChain/outbox 和后台模型调用已有源码接线，目标环境真实 Provider 闭环仍待验收。

审计记录字段：操作者、租户、应用、操作类型、目标对象、时间、来源 IP、结果及变更摘要。管理端提供按操作编码、结果、目标类型/ID、操作者、租户和时间范围组合筛选，支持服务端分页与只读详情查看。

不得记录密码、完整令牌、客户端密钥或模型密钥明文。审计记录仅允许有权限人员查询，不提供修改和删除入口。

## 8. 数据与权限模型

核心实体：

```text
User（全局身份）
 └── TenantMembership（用户在租户中的成员身份）
      ├── Organization / Group
      └── RoleBinding（租户/应用内角色绑定）
           └── Role → PermissionGrant
                           ├── ResourceType / Resource
                           └── Scope（read/create/update/delete/...）

Tenant
 ├── Application（OIDC Client + 登录品牌）
 ├── AuthorizationPolicy
 └── ThemeSettings（平台/租户/用户外观令牌）
```

建议核心表：

| 表 | 说明 |
|---|---|
| tenants | 租户及租户状态 |
| applications | 应用和 OIDC 客户端配置 |
| oauth_consent_requests | 一次性授权同意票据摘要及绑定的授权上下文（短时有效、可消费一次） |
| users | 全局用户身份、账号及验证状态 |
| tenant_memberships | 用户与租户成员关系、成员状态 |
| organizations | 租户内组织结构；父组织采用同租户复合外键 |
| membership_organizations | 租户成员与组织多对多归属、唯一主组织；数据库复合外键禁止跨租户关联 |
| role_data_scopes | 角色对权限配置 tenant/self/organization/tree/selected 过滤范围 |
| roles | 租户或应用范围内的角色 |
| permissions | 稳定菜单/功能/API 权限编码、`catalog_namespace`（与 OAuth 应用 `permission_namespace` 对齐）、资源类型、Scope 与 active/disabled 生命周期状态 |
| role_permissions | 角色与权限关系 |
| user_roles | 成员关系范围内的用户角色绑定 |
| resources / scopes | 受保护资源类型和允许操作 |
| permission_grants | 角色或主体对资源及 Scope 的授权 |
| data_policies | 数据范围及属性条件策略 |
| application_themes | 应用登录品牌配置及版本 |
| oauth_authorization_codes | 一次性授权码摘要、客户端/用户绑定、精确回调、nonce、PKCE challenge 和过期/消费状态 |
| oauth_refresh_tokens | OAuth 刷新令牌摘要、客户端/用户/范围、轮换族及撤销状态 |
| theme_preferences | 平台、租户和个人管理台外观配置 |
| sessions | 活跃会话和设备信息 |
| audit_events | 登录及管理审计记录 |
| models / model_policies | 租户模型目录和模型调用授权策略 |
| model_usage_events | 网关上报的 append-only Token/结果/延迟/费用估算账目；request ID 唯一，不存输入输出正文 |
| user_groups / user_group_memberships / user_group_roles | 租户内用户组、组成员和组角色继承关系；复合外键约束组、成员和角色必须属于同一租户 |

核心业务表应包含 `tenant_id` 或明确的租户归属关系。所有授权查询必须从已验证的身份上下文获得租户范围，不能信任请求体中的租户标识。

## 9. 接入规范

### 9.1 认证协议

采用 OAuth 2.0 / OpenID Connect 授权码流程。访问令牌应短期有效；刷新令牌需支持撤销和轮换。令牌只携带必要且稳定的身份声明，复杂数据权限通过授权查询或业务侧策略获取。

### 9.2 业务系统职责

接入系统必须：

- 校验令牌签名、签发方、受众、有效期和随机状态参数。
- 在服务端校验 API、数据和资源级权限。
- 所有在线 IAM 授权请求必须有明确的超时上限；SDK 默认 3 秒，服务端可调整，超时或网络故障须按 503 失败关闭，不得因此访问受保护资源。
- 在请求上下文中绑定用户 ID、租户 ID 和应用 ID。
- 可将本 Provider 的 RS256 access token 发给 `POST /api/v1/authorization/check`；调用时 tenant 必须等于签发 token 的 `tenant_id`，应用可省略（默认 token 对应应用），不可切换到别的应用。管理接口只使用 IAM 管理会话，不能把 OIDC 客户端 token 当平台管理员凭证。
- 对知识库召回、导出、删除等敏感操作执行细粒度权限检查。
- 避免将客户端密钥、模型密钥或长期令牌放在浏览器。

### 9.3 首批接入顺序

1. **DeerFlow（唯一首批试点）**：先完成 IAM 平台验收，再验证 OIDC 登录、在线权限、Agent 模型/工具授权、资源查询隔离、目标数据库迁移和浏览器闭环。
2. 只有 DeerFlow 端到端验收通过后，才重新评审是否接入其它业务系统；AI Resume 与 Knowledge Base 的旧 IAM 接入代码已清理。
3. 模型目录/配额仅通过 DeerFlow 试点验证实际服务端调用链，未完成真实 Gateway 前不启用配额 enforcement。

### 9.4 服务端 SDK 与简单接入目标

现有 Python 与 TypeScript SDK 提供 OIDC relying-party、在线授权和数据范围辅助能力；具体方法、身份绑定、超时及错误处理见 [技术架构与接入](技术架构与接入.md)。业务服务端使用已验证身份建立自己的安全会话，令牌和密钥保留在服务端。

用户确认多项目底座需要降低接入复杂度。目标流程为：登记应用 → 填写服务端配置 → 安装框架适配并声明权限 → 分配角色后验收。将 OIDC 回调、令牌验签与轮换、在线判权和标准错误处理封装在共享适配层；业务方主要声明业务权限并执行本地资源归属检查。该流程是本轮形成的方案，框架插件、应用初始化向导和权限清单导入尚未实现。

基础接入以登录、功能权限及 owner-only 为主；组织共享、资源实例授权、模型计量按业务需求启用。默认不增加业务用户管理后台。权限码以应用命名空间区分；应用或租户不匹配、缺少授权、超时和无效响应均拒绝。前端权限提示服务于交互展示，业务接口仍在线判权。

简单接入验收需覆盖两个应用不能互用授权、两个用户不能互读本人资源、撤权后的在线拒绝、IAM 故障时不执行受保护操作、会话刷新与本地登出。接入效果以真实示例项目运行证据为准，源码封装完成不能代替验收。

## 10. 非功能需求

### 10.1 安全

- 密码使用强哈希算法存储，并执行长度及常见弱密码校验。
- 登录失败次数、锁定时间、验证码和会话时长可配置。
- 服务端对所有管理接口和业务授权接口实施权限检查。
- 令牌、验证码、密钥等敏感信息不得进入普通应用日志。
- 采用 HTTPS 部署；敏感配置和密钥加密保存。
- 重要授权变更可追溯，并能使相关会话或授权缓存失效。

### 10.2 兼容性和体验

- 管理后台适配主流桌面浏览器。
- 窄屏管理导航必须让所有主要页面入口可发现；列表搜索/筛选在窄屏下不得横向挤压或溢出。
- 登录页适配桌面端和移动端。
- 所有表单明确展示必填项、校验规则和失败原因。
- 删除、停用、发布等影响范围较大的操作需提供二次确认和结果反馈。

### 10.3 可扩展性

- 首期采用模块化单体，按身份、应用、组织、授权、主题、审计划分模块。
- 授权接口和权限编码保持稳定，支持新增业务应用和权限类型。
- 为权限查询缓存设计授权版本或失效通知机制。
- PostgreSQL 作为主数据存储；登录主题图片等静态资源存储在对象存储。

## 11. 验收标准

1. 管理员可创建租户和应用，并登记合法的登录与登出回调地址。
2. DeerFlow 可通过统一登录中心完成 OIDC 登录与回调；首登只创建普通用户，不能由邮箱或本地配置提权。
3. 未登记的回调地址无法获得授权码或令牌。
4. 不同应用可使用不同的 Logo、背景、颜色、布局及文案，并可预览和发布。
5. 管理员可创建租户范围角色，按资源和操作 Scope 配置权限并分配给租户成员。
6. 未授权用户无法通过直接调用后端接口执行受限操作。
7. 禁用用户不能新登录或刷新令牌。
8. 同一个全局用户加入多个租户后，在各租户拥有独立且互不继承的角色；管理员可签发有时限的租户角色邀请，撤销、过期或重复接受均不能授予权限，停用成员接受新邀请不得恢复旧角色。
9. DeerFlow 项目与会话查询须执行 IAM `data_scope` 与本地 owner 交集，跨用户/租户越权请求失败关闭。
10. 管理台可切换浅色/深色、品牌主色和界面密度；个人主题覆盖租户默认值。
11. 每个应用可独立配置登录页品牌，且管理台外观变更不影响登录页。
12. 登录、用户状态变化、角色变更、应用配置和主题发布均可查询审计记录。
13. 浏览器端不包含客户端密钥、模型密钥或服务端长期凭证。
14. 租户管理员仅能查看其获授权租户的成员、组织与角色数据范围；`org.read` 只读，`org.manage` 可读写；直接调用接口仍须由后端按目标租户鉴权。
15. 运维人员能够用受校验的数据库备份恢复到隔离临时库，并确认 Alembic revision 与核心身份表存在；生产环境还须单独演练 API readiness、OIDC 密钥恢复和客户端登录，不能把备份文件可读等同于灾备通过。

## 12. 指标建议

首期上线后关注以下指标：

- 登录成功率及登录失败原因分布。
- 单应用接入所需的开发和配置时间。
- 授权错误或越权事件数量。
- 用户权限变更生效时延。
- 登录主题配置发布成功率。
- 审计事件完整率。

指标阈值需结合首批接入量和实际部署环境在技术评审时确定。

## 13. 风险与应对

| 风险 | 应对方式 |
|---|---|
| 各项目权限实现不一致 | 统一权限编码、OIDC 接入规范和服务端鉴权示例 |
| 权限撤销后离线业务服务仍接受已签发访问令牌 | 管理及 OIDC access JWT 支持按 `jti` 撤销，IAM 在线授权接口/UserInfo 与 RFC 7662 introspection 会拒绝已撤销令牌；离线验签服务须使用在线 introspection/授权或接受令牌到期前的传播延迟 |
| 数据权限规则快速膨胀 | 首期采用标准数据范围，按真实业务场景迭代扩展 |
| 登录主题配置引入脚本风险 | 仅提供受控主题参数和资源上传，不执行任意脚本 |
| 多产品接入的映射差异与实施跨度 | 先验收 IAM 平台和 DeerFlow 唯一试点；通用 SDK/框架封装降低后续项目接入成本，其他产品在试点后评审，任何产品均须分别验收权限与数据过滤 |
| 将认证授权过早拆成微服务增加复杂度 | 首期模块化单体，达到明确容量或团队边界后再拆分 |
