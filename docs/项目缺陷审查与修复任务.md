## P1：租户管理员应用守卫没有收紧目标租户边界

**证据**

- `backend/app/services/admin_authorization.py` 的 `AdminAccessGuard.has_application_admin_access()` 在检测到操作者具有租户级范围后，对未轮换密钥的操作直接返回 `True`，该分支没有验证操作者在 `tenant_id` 中是否有活动成员身份。
- `backend/app/api/v1/admin/applications.py` 的应用资料更新、状态变更等单项接口调用该守卫。`backend/app/api/v1/tenant_admin/application_models.py` 和 `application_roles.py` 的应用工作台入口也依赖它。
- `docs/产品需求.md` §3.2 要求租户级数据边界限定为操作者所有租户；“所有”仍须由该操作者的活动租户成员关系确定。

**影响**

持有某租户 `tenant.admin` 的用户，在知道另一个租户应用 ID 的情况下，可能通过单项应用接口读取或修改对方应用。列表接口使用 `list_readable_application_capabilities()` 并有成员关系检查，不能弥补单项接口守卫的缺口。

**修复目标**

- 超管仍可全域代管。
- 非超管在租户级分支必须验证其对目标租户的活动成员关系，并在需要时验证目标租户有效状态。
- 应用级操作者继续受应用绑定与对应菜单/按钮节点约束。
- 不要仅通过隐藏前端入口修复；服务端守卫和所有调用路径必须一致。

**验收条件**

- 仅属于租户 A 且持有 `tenant.admin` 的操作者，对租户 B 应用的读取、资料更新、停用/启用、角色与模型工作台访问均被拒绝。
- 同一操作者对其所属租户仍保留需求规定的权限；超管仍可代管。
- 增加覆盖守卫和代表性单项 API 的隔离测试，避免只验证列表过滤。

## P1：`my-models` 未绑定请求应用与已验证身份

**证据**

- `backend/app/api/v1/authorization.py` 的 `list_my_models()` 用查询参数 `client_id` 选择目标应用，只检查调用用户是否为该租户的活动成员，然后返回该应用的三级下发交集。
- `current_user()` 对 OIDC token 已验证并设置 `_oidc_application_id`，但 `list_my_models()` 没有将它与请求 `client_id` 对应的应用比较，也没有单独确认用户属于目标应用。
- `docs/应用对接.md` §9 与 `docs/产品需求.md` §6.4 将此定义为“本应用”模型清单。

**影响**

同一租户中持有应用 A token 的用户可以把 `client_id` 改为应用 B，读取 B 的模型名称、能力、限额和价格等配置，即使该用户没有应用 B 的访问关系。

**修复目标**

- 将目标应用绑定到服务端验证的身份上下文，禁止 OIDC token 跨应用查询。
- 如管理会话也需要调用该端点，必须单独定义并服务端验证管理会话的目标应用可见性；不可只依赖调用者可控的 `client_id`。
- 对无权目标应用采取一致的默认拒绝策略，不返回其模型清单。

**验收条件**

- 同租户用户持应用 A 的 OIDC token 请求应用 B 的清单时被拒绝或得到契约定义的空结果，不能得到 B 的任何模型字段。
- 有效的应用 B 身份仍可获取其三级下发交集；跨租户行为继续防止枚举。
- 增加同租户跨应用测试。现有测试只验证外租户用户，不能覆盖此情形。

## P1：模型判权仍依赖旧的模型租户归属

**证据**

- `backend/app/api/v1/admin/models.py` 创建模型时把目录行归属统一的平台租户。
- `backend/app/services/authorization.py` 的 `AuthorizationEvaluator.evaluate_access()` 对 `model.invoke` 仍要求 `ModelCatalog.tenant_id == 请求 tenant_id`。
- `backend/app/api/v1/model_usage.py` 的预留契约要求网关先调用 `/authorization/check` 并确认 `model.invoke`。
- `docs/产品需求.md` §6.4 已规定模型授权唯一依据是平台目录、租户下发和应用下发关系，不由业务权限码或资源树判定。

**影响**

非平台租户调用已下发的模型时，旧租户归属检查会拒绝授权；按当前预留接口说明接入的网关因此无法完成调用前检查。`backend/app/services/permission_impact.py` 也仍按模型行租户过滤 `model.invoke` 影响范围。

**修复目标**

- 让在线判权与 §6.4 的三级下发规则一致：模型 active、租户下发 active、应用下发 active，并验证已验证用户对目标应用有访问关系。
- 明确 `model.invoke` 在当前权限体系中的地位。若它不再是模型调用授权依据，同步调整网关契约、相关调用方和权限影响分析；不要保留一个必然失败的前置检查。
- 保持配额 enforcement 的上线门禁，不因修复模型判权而默认开启配额拦截。

**验收条件**

- 已下发模型通过调用前检查；未下发、已回收、停用、错误租户/应用的模型均默认拒绝。
- 预留流程的前置授权步骤与上述判权结果一致。
- 权限模拟/影响分析不再依赖平台模型行与业务租户 ID 相等。

## P2：权限模型导航与权威需求文档冲突

**证据**

- `docs/产品需求.md` §3.3 已说明管理面唯一目录是菜单/按钮树，旧 27 个五域接口码目录已下线。
- `AGENTS.md`、`ai/02-架构与权限/权限模型.md`、`ai/07-术语表/术语表.md`、`ai/01-项目概览/目录地图.md` 仍把 27 个五域码描述为当前管理面权限模型。
- `backend/app/db/seed_greenfield.py` 的初始化注释也仍称写入旧 27 个五域接口码。

**影响**

维护者或后续模型可能按已下线目录新增判权、页面或种子逻辑，造成前后端权限口径偏离。

**修复目标**

- 以产品需求与 `permission_kinds.py` 的当前实现为准，更新上述导航和注释。
- 区分管理面菜单/按钮节点与应用业务权限码；明确 `rbac_guards.py` 是节点判权/范围守卫，而非旧 27 码目录。
- 保留历史记录中的旧模型事实，但标注为已废弃，避免写成现状。

**验收条件**

- `rg` 搜索当前导航与源码注释，不再把旧 27 码描述为现行管理面权限目录。
- `ai/README.md`、模块导航和根目录约定与产品需求及实现一致。
