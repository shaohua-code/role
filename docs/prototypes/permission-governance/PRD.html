权限闭环治理方案

保持现网权限模型语义不推翻，用「单一口径 + 一致性门禁 + 体检排障」把平台权限与角色分配收成一个可验证的闭环。

背景：乱的不是模型，是实现层的双轨

2026-10-30 四类权限树（菜单 / 按钮 / 数据 / 接口）与五级平台角色（L1 / L3 / 多应用 / L2 / L4）落地后，产品语义已经收敛：三层配权、看得见才能配、租户隔离都有明文。本轮对前后端全量侦察（2026-10-30），确认「乱」来自 16 处实现层双轨、漂移与死代码，典型后果：

  • 看得见却进不去：角色持 menu.users 但缺 platform.account.read，侧栏能点、列表 403（挂码弹窗只提示不阻断）。
  • 没码也能过：后端 ensure_codes 保留「五级模板角色 key 回退」——前端按码裁剪、后端认角色 key，同一事实两套口径。
  • 一份映射两处维护：菜单↔按钮↔接口映射在后端 permission_kinds.py 与前端 permissionTree.ts 各写一份，靠人工同步。
  • 新旧并行：数据范围 *.scope.* 叶子码与存量 RoleDataScope 双读；资源树与权限目录两套体系语义重叠。

产品契约

主用户平台超级管理员（L1）——治理动作的发起与复核者；L3 / 多应用 / L2 在各自范围内受益（不再遇到「看得见进不去」）。
触发配权结果与预期不符：进页 403、改码不生效、码表对不上、审计对不上账。
核心任务让「定义 → 呈现 → 挂码 → 分配 → 判权 → 审计 → 体检」七环单口径，每个乱点可发现、可定位、可修复、可复检。
完成条件权限体检页 0 阻断 0 告警；任意用户「生效链路」一次查全；码表映射仅一处定义且有测试门禁。
共享对象权限码（permission）及其上的角色授权（grant）。

闭环

① 定义
码表契约唯一源→ ② 呈现
目录 / 树由契约生成→ ③ 挂码
看得见才能配 + 阻断→ ④ 分配
成员绑定唯一入口→ ⑤ 判权

变更留痕 + 失效→ ⑦ 体检

第⑤环是本轮裁决核心：判权只认码。模板角色 key 只用于种子发放与 UI 标注，不再参与运行时判权。

决策与假设

  • 已裁决（历史）：五级模板、27 接口码、四类树、看得见才能配——维持不变（P392 / P405 / 2026-10-30 收口）。
  • 本方案裁决：判权只认码（D2）、映射单一来源（D3）、对齐即门禁（D4）、数据范围以叶子码为主路径（D5）。
  • [Assumption, TBD] 去角色 key 回退需要一个迁移窗口：先「体检告警 + 日志观察」，确认 0 命中后切换为拒绝。窗口长度由实施方排期定。
  • [Assumption, TBD] 存量 RoleDataScope 迁移需一次性 map-data-scope-to-codes 入库执行（需数据库迁移授权，按部署门禁走）。

需求明细

按闭环七环组织；每条给规则、边界与原型对应。P0 = F1–F4，P1 = F5–F8。

F1 权限体检页 P0

目的：把「乱」从人肉走查变成一眼可见的检查项清单——发现、定位、修复、复检闭环的入口。

页面责任：高级管理新增「权限体检」。顶部三卡（阻断 / 告警 / 通过计数），下方检查项列表；每项含名称、判定说明、状态、详情入口。

检查项（初版八项）

编号检查级别判定
H1菜单-接口对齐阻断任一角色持 menu.* 缺其映射的任一接口码
H2按钮映射唯一性告警button.* 映射 ≥2 个接口码，或与其他按钮码集合重叠

规则

  • 触发时机：进入页面即运行；挂码保存、种子执行、迁移完成后服务端置「待复检」，页头提示。
  • 详情抽屉给出受影响角色 / 成员计数与修复动作；修复一律走既有「预览 → 保存」链路，不旁路。
  • 阻断级不阻止操作，但作为发布门禁输出（与测试断言同源，见 F2）。
  • 可见性：仅 L1（页面挂在高级管理下，随菜单码裁剪）。

F2 码表契约：映射单一来源与门禁 P0

目的：菜单↔按钮↔接口映射、层级码集只允许一处定义；前端零硬编码。

  • 唯一源：后端 permission_kinds.py 为契约唯一源；GET /admin/permissions/tree 下发完整映射（含 menu → button[] → api[] 与层级可见集）。
  • 前端消费：permissionTree.ts 的 MENU_RELATED_APIS / BUTTON_RELATED_APIS / MENU_BUTTONS / MENU_GROUPS 硬编码全部删除，改为消费 tree 响应或构建期生成物；permissionGroups.ts 的 PLATFORM/TENANT_SCOPE_CODES 与「27/20/16/15」文案改由常量接口下发。
  • 门禁：后端测试断言「H1–H6 检查全通过」作为 CI 门禁（与体检同源同判定），防止回归。
  • 修正项：button.roles.manage 收敛为只映射 rbac.role.manage（组织写归 button.org.manage）；grant_codes_skip_missing 缺码时不再静默——报错或体检告警。

F3 判权口径收口：只认码 P0

目的：消灭「有角色无码也能过」——前端裁剪与后端判权同一事实。

  • 裁决 D2：运行时判权只看「有效角色 × 挂码并集」；ensure_codes 的 role_keys 回退移除。模板角色 key 仅用于：种子发放、UI 模板标签、体检归属展示。
  • 迁移窗口：先记录回退命中（日志 + 体检 H3 计数），确认归零后切换为拒绝；模板角色由种子保证码集完整，因此正常环境回退命中恒为 0。
  • 绑定豁免收紧：绑定已存在时同样走判权校验（去掉直接 return）；grantable 参数必传，L1 显式传全量而非 None 语义。
  • 敏感码双检统一：_SENSITIVE_CODE_DUAL_CHECK 从单码扩为按「写类按钮码」清单统一处理。

边界：L1 整段放行维持不变（平台超管语义）；租户隔离与数据范围判定不受本条影响。

F4 数据范围收口：叶子码主路径 P0

目的：结束 *.scope.* 叶子码与 RoleDataScope 双读双写。

  • 目标态：evaluate_access 只读数据叶子码授权；RoleDataScope 表保留为只读归档直至下轮删除。
  • 迁移：一次性执行 map_role_data_scopes_to_codes（已存在实现）把存量策略映射为叶子码授权；迁移需受保护备份 + 明确授权（部署门禁）。迁移后重跑体检，H4 归零。
  • 写路径收口：数据范围替换接口改为写叶子码授权（或双写一过渡期后停旧表）。
  • 分级修复：恢复写分级——数据范围策略写操作要求 org.manage 且 L3 起（L2 只读），删除当前的参数弃用写法。

F5 挂码弹窗目标态：缺口阻断 + 影响预览 P1

目的：把「看得见才能配」贯彻到保存一刻——配出必然 403 的授权直接被拦下。

  • 缺口阻断：勾选 menu.* 而其映射接口码未全勾时，「保存授权」置灰并明示缺失码清单（现仅文案提示）。
  • 影响预览：顶部常驻「影响 N 名成员 / 新增 X / 移除 Y」；保存走既有 preview + 乐观锁两段式。
  • 层级与来源标注：每个码带层级起点标签（仅平台超管 / 租户管理员起 / 应用管理员起）与模板 / 自定义来源；不可见码不出现。
  • 与体检联动：弹窗内阻断与体检 H1 同一判定，显示「即体检 H1」链接。

F6 排障链路：成员与生效 P1

目的：「用户为什么进不去 / 为什么能进」一次查全，替代逐表人肉核对。

  • 按用户 + 上下文（租户 / 应用）展示：有效角色（直绑 / 组继承来源）→ 持码按四类分组 → 对所选页面 / 接口的命中结果（放行原因或 403 缺码）。
  • 复用既有持有者反查与鉴权模拟能力；本需求是「把已有零件接成一条链路」，不新建判权逻辑。
