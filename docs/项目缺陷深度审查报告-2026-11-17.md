# 项目缺陷深度审查报告

审查日期：2026-11-17  
审查基线：当前工作区（含暂存与未暂存改动）  
审查类型：静态代码与文档审查  
运行验证：未运行测试、构建、浏览器走查或目标环境探测

## 摘要

当前工作区确认存在 3 项高优先级问题：租户管理员应用访问缺少目标租户成员关系校验、OIDC 用户可读取同租户其他应用的模型清单、`model.invoke` 判权仍按旧模型租户归属检查，和新三级分发契约冲突。

另确认 2 项中优先级问题：模型目录对象读取/下发接口没有强制平台租户归属；项目导航仍将已下线的 27 个五域权限码写成现行规则。下列结论均为源码静态判断，尚未通过运行测试复现。

## P1：租户管理员可越过目标租户边界访问应用

**位置**

- `backend/app/services/admin_authorization.py`：`AdminAccessGuard.has_application_admin_access()`，租户级范围分支。
- 该守卫被 `backend/app/api/v1/admin/applications.py`、`backend/app/api/v1/admin/application_resources.py`、`backend/app/api/v1/tenant_admin/application_roles.py` 和 `application_models.py` 复用。

**证据与原因**

非超管进入租户级范围分支后，守卫没有验证操作者是否在传入的 `tenant_id` 中具有活动成员关系，普通应用读写会直接放行。`scope_at_least()` 取操作者跨所有成员关系的最高角色范围，不能证明其属于本次请求目标租户。

**影响**

只在租户 A 有 `tenant.admin` 的用户，可能通过猜测或获得租户 B 的应用 ID 读取或修改应用资料、资源、角色或模型分配。当前应用列表另有成员过滤，但无法保护这些按 ID 访问的单项端点。

**修复与验收**

- 非超管租户级访问必须验证目标租户的活动成员关系；超管代管行为保持不变。
- 对目标应用的读取、资料更新、状态变更、角色、资源和模型工作台接口增加跨租户拒绝覆盖。
- 覆盖同租户正常操作及超管代管的正向用例，避免修复造成合法访问回归。

## P1：`my-models` 允许 OIDC 身份跨应用读取清单

**位置**

- `backend/app/api/v1/authorization.py`：`list_my_models()`。
- `backend/app/core/security.py`：`current_user()` 已将验证后的 OIDC 应用上下文写入 `user._oidc_application_id`。

**证据与原因**

接口根据调用者传入的 `client_id` 选择目标应用，仅检查用户属于目标租户，没有将目标应用与 `_oidc_application_id` 比较，也没有要求该用户属于该应用。它随后返回目标应用的已下发模型集合。

**影响**

持应用 A 有效 OIDC token 的同租户用户可以将 `client_id` 改为应用 B，读取 B 的模型 key、名称、能力、限额和价格，即使没有应用 B 的访问关系。当前 `backend/tests/test_model_distribution.py` 仅检查外租户用户返回空集合，未覆盖同租户跨应用。

**修复与验收**

- OIDC 请求必须以已验证 token 的应用为查询范围，不信任客户端传入的应用身份。
- 若管理会话也需要使用此接口，另行定义并验证管理会话的数据边界。
- 添加同租户 A token 查询 B、正确应用身份查询本应用、外租户访问等用例；未授权响应不得含目标应用模型字段。

## P1：`model.invoke` 判权沿用已废弃的模型归属语义

**位置**

- `backend/app/api/v1/admin/models.py`：新目录项统一归属平台租户。
- `backend/app/services/authorization.py`：`AuthorizationEvaluator.evaluate_access()` 对 `model.invoke` 检查 `model.tenant_id == tenant_id`。
- `backend/app/api/v1/model_usage.py`：预留接口文档要求网关先通过 `/authorization/check` 的 `model.invoke` 检查。
- `backend/app/services/permission_impact.py`：影响分析仍按 `ModelCatalog.tenant_id == role.tenant_id` 找模型。

**证据与原因**

模型目录已统一存于平台租户，而产品需求 §6.4 明确三级下发关系是模型授权唯一依据。授权判定和影响分析仍用模型行租户归属作为门槛，未查询租户下发与应用下发关系。

**影响**

对非平台租户而言，已正确下发的模型仍可能在 `/authorization/check` 被拒绝；按预留接口说明工作的网关因此无法通过调用前检查。与此同时，若只移除旧归属条件而不检查三级授权，则会产生反向的越权风险。

**修复与验收**

- 先明确 `model.invoke` 是否仍是业务调用授权的一部分；统一产品契约、`/authorization/check`、用量预留前置步骤和权限影响分析。
- 如保留该检查，按活动模型 + 活动租户下发 + 活动应用下发 + 用户对目标应用的有效访问关系判定。
- 已下发模型应放行；未下发、回收、停用、错误租户/应用必须拒绝；模拟与影响分析使用同一口径。
- 配额 enforcement 继续默认关闭，修复不得隐式开启拦截。

## P2：模型目录接口没有强制平台租户归属

**位置**

- `backend/app/api/v1/admin/models.py`：`_get_platform_model()` 仅按 ID 读取 `ModelCatalog`，没有验证 `tenant_id` 属于 `slug=platform` 的平台租户。
- `update_model()`、状态变更、删除、租户下发列表及下发/回收端点均以该 helper 或相同的 ID 查询为基础。
- `ModelDistribution.grant_to_tenant()` 和 `grant_to_application()` 验证模型状态与 grant，但没有验证目录行属于平台租户。

**证据与原因**

列表与创建路径按平台租户限制目录项，但按 ID 的操作没有复用这一边界。如果库中存在历史、误建或其他来源的非平台模型行，平台目录 API 可将其修改或下发，用户界面看不到该行而 API 会接受它。

**影响**

平台模型目录“所有目录行属于 platform 租户”的不变式仅由创建路径保证；其他写入或存量异常可绕过，导致非平台模型被当成全平台模型传播。

**修复与验收**

- 统一按 ID 加载平台模型的入口：必须同时确认目录行 `tenant_id` 等于平台租户 ID，不符合时按 404 处理。
- 对领域服务入口也明确验证平台模型归属，避免未来其他调用方绕过 API helper。
- 添加非平台目录行不能被更新、删除或下发的测试；添加正常平台目录行可操作测试。

## P2：权限模型导航与当前产品及代码不一致

**位置**

- `AGENTS.md` 仍要求按五域 27 码判权。
- `ai/02-架构与权限/权限模型.md`、`ai/07-术语表/术语表.md`、`ai/01-项目概览/目录地图.md` 仍把五域码写成当前管理面模型。
- `backend/app/db/seed_greenfield.py` 初始化注释仍称写入 27 个五域接口码。
- `docs/产品需求.md` §3.3 已明确管理面唯一目录为菜单/按钮树，旧 27 码目录已删除。

**影响**

维护者会同时读到互相冲突的权限规则，可能恢复废弃码表、将业务码与管理面节点混用，或采用错误的路由判权方案。

**修复与验收**

- 以产品需求与 `backend/app/services/permission_kinds.py` 为当前权威，同步根目录说明、`ai/` 导航和种子注释。
- 历史记录可以保留旧五域码，但须明确标为历史/废弃，不可作为现行规范。
- 搜索当前规范与源码注释，确认不再将五域 27 码描述为现行管理面目录。

## 检查范围与未验证事项

本次静态检查覆盖产品需求、后端权限守卫、应用/角色/资源/模型接口、OIDC 身份上下文、模型用量调用前契约、模型分发服务、相关测试用例和 AI 导航文档。未逐一执行所有端点，也未做动态安全测试。

未运行：后端测试、前端类型检查与构建、浏览器验收、生产预检、数据库迁移或运行环境探测。因此不能据此认定缺陷已动态复现，也不能认定未列出模块不存在其他问题。工作区已有其他暂存/未暂存改动，本次报告没有改变那些源码。

## 建议修复顺序

1. 修复目标租户访问守卫，并补跨租户单项接口测试。
2. 将 `my-models` 查询范围绑定到已验证应用身份，并补同租户跨应用测试。
3. 统一 `model.invoke` 与三级下发判权契约，覆盖用量预留链路。
4. 对模型按 ID 操作增加平台租户归属校验。
5. 修正权限导航与种子注释，再执行受影响的隔离测试和前端/SDK检查。
