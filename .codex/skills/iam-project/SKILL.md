## Product invariants

- Centralize authentication and policy management; business services enforce authorization for their own resources.
- Email password reset is an IAM-managed SMTP flow with hash-only single-use tokens, generic account-enumeration-resistant responses, and per-email cooldown. The email link encodes its token once in the `#password-reset=` fragment, never in the query string; the frontend captures it then immediately strips authentication fragments from the current URL/history entry. After reset, `auth_version` invalidates old IAM online sessions and revokes IAM/OIDC refresh credentials; it cannot clear a connected product's local cookie/session, and offline OIDC JWT consumers retain the token's remaining lifetime. `0011_password_reset_sessions` is source-authored but must not be called deployed until a PostgreSQL migration run is confirmed. ## Security implementation notes

- Derive trusted tenant context from the current user’s persisted active membership. A tenant ID in a request is only a lookup/filter input and must be checked against that membership.
- Admin mutation and its audit event belong in one transaction. Never serialize password hashes, JWTs, client secrets, or model-provider secrets into API responses or audit details.
- Permission codes are stable identifiers; decisions default to deny and must be made by backend APIs. A menu or UI visibility check is never sufficient authorization.
- Every online authorization request needs a finite timeout. The shipped Python and TypeScript authorization clients default to 3 seconds; the TypeScript OIDC relying-party client defaults to 5 seconds per HTTP request. Timeout, transport error, invalid response, or missing data scope must fail closed. Do not add automatic authorization retries without idempotency, latency, and load review; never retry OIDC code exchange or refresh rotation after an ambiguous network failure.
- Permission status `disabled` must be excluded from live authorization and new role grants. Preserve historical grants/data scopes; explicit reactivation restores grants not removed while disabled, so administrator UX must warn before restore. Status changes are audited in the same transaction and use `expected_status` to reject stale updates.
- Redirect URIs must be parsed and validated against the exact registered value. Theme fields remain allow-listed; block JavaScript, arbitrary CSS/HTML, protocol-relative URLs, and untrusted schemes.
- Where the code has not yet met a product invariant (notably OIDC or data-level filtering), update both implementation status and PRD acceptance/version tracking rather than suggesting that configuration alone enables it.
